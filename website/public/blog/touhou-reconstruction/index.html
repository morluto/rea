Reconstructing Touhou with AI agents.

From individual expertise to a repeatable workflow. Lessons from continuing TH08, starting TH095, and rebuilding TH04 for PC-98.

1. Decide what you want to build

Open with a practical question: do you want to understand a game, rebuild it, move it to another platform, or change how it plays?

  • Reconstruction: recover source and check it against the original program.
  • Port: make that source work with a new platform’s rendering, input, audio and files.
  • Mod: understand a behavior, change it deliberately, then test the result.

Planned figure: one recovered codebase branches into a faithful build, a port and a mod. Each branch names its own success check.

2. Turn expertise into a repeatable process

The industrial-age analogy: agents do the work, tools let them inspect the program, checks test the result, and the repository preserves what they learned.

  • Make the task small enough to check. One behavior or connected subsystem has a clear input, output and test.
  • Make feedback fast. A compile error, mismatch or runtime failure tells the agent what to investigate next.
  • Make experience reusable. A lesson becomes a script, test, evidence note or handoff that survives the conversation.

Standardize the checks and the handoff; leave the investigation flexible. REA fits at the inspection step: it gives the agent code, references and observations. Source reconstruction and project validation complete the loop.

5. TH04: keep the method, rethink the assumptions

PC-98 changes the practical problem. The game spans four DOS programs and depends on older hardware behavior. Existing ReC98 work supplies valuable knowledge; the new reconstruction still needs its own checks.

  • Map the whole product: startup, menus, gameplay, endings and the resident component.
  • Show why one excellent function percentage can leave important parts of the game untested.
  • Adapt the comparison and runtime checks to the platform. Feed discoveries back into reusable tests.
  1. 6 SepReconstruction repository bootstrapped.
  2. 26 Sep661 / 663 reviewed game functions accepted across four programs.
  3. 2 OctFour standalone DOS products built, about 26 days after bootstrap.

Lesson: reuse the process, then verify the assumptions that the new platform changes.

6. Run small experiments and keep useful checkpoints

Bring the three stories together into a working loop a reader can use.

  1. Establish a baseline. Identify the exact target and rerun the checks that matter to this task.
  2. Pick one question. Choose a behavior or subsystem with a result you can inspect.
  3. Gather evidence. Follow the code that reads or changes a value, and the functions that call it; name what is known and what still needs testing.
  4. Reconstruct and check. Compare the affected code, build the program, and exercise relevant behavior.
  5. Commit and hand off. Keep source, evidence, failed hypotheses and the next task in the repository.

Explain how this loop continues across fresh agent sessions. Turn a recurring failure into a test so the next game benefits from it.

Planned figure: a failing experiment returns to investigation; an accepted batch feeds both the next task and the shared knowledge base.

7. Use the recovered source for ports and mods

Explain the payoff: source with meaningful names, clear ownership and reproducible checks is something you can change with confidence.

  • Use TH08’s Linux and Web products to illustrate replacing platform services while preserving game logic.
  • Show how a small mod begins with one recovered rule and a controlled change.
  • Connect the desired outcome to its checks: faithful behavior, a working new platform, or an intentional gameplay difference.

Planned figure: checked reconstruction → readable source → portable backend or a deliberate gameplay change.
