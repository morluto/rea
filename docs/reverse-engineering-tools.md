# Reverse-engineering tool integrations

REA can call caller-supplied GNU objdump, GDB, Rizin, and Cutter installations. REA does not install or update these tools. Static objdump/Rizin and Cutter workflows use the same services from CLI and MCP. GDB and Rizin debugger operations use the same session-manager implementation; MCP exposes persistent sessions, while CLI debugger commands are ephemeral. Persistent MCP debugger sessions exist only for the lifetime of the REA MCP server process. Cutter connects to an already-running upstream GUI through REA's plugin and loopback bridge.

## GNU objdump

`inspect_with_objdump` and `rea inspect-with-objdump` capture stdout and stderr as inline Evidence. Evidence records SHA-256 digests before and after the provider call and whether those observed digests differ; this cannot prove the exact bytes consumed if the artifact changes during execution. Choose one operation: `file_headers`, `section_headers`, `symbols`, `relocations`, `dwarf`, `disassemble`, `disassemble_all`, or `architectures`. `disassemble` maps to `-d`; `disassemble_all` maps to `-D` and has different symbol-boundary semantics. `architectures` maps to `-i` and reports BFD targets compiled into the installed binary, not a guarantee that a target is supported.

For DWARF, REA explicitly controls debug-link following. It follows local debug links by default; set `follow_debug_links` to `false` to pass `-WN`. The CLI option is `--follow-debug-links false`. REA clears `DEBUGINFOD_URLS` in the objdump child environment to disable debuginfod network access on GNU binutils versions that do not support `-WE`. The complete raw output is authoritative; REA does not normalize it into a version-independent disassembly schema.

```sh
rea inspect-with-objdump ./program disassemble
rea inspect-with-objdump ./program dwarf --follow-debug-links false
```

Captured stdout and stderr are each limited to 16 MiB (32 MiB combined); `output_truncated` marks output beyond either stream limit.

## GDB

`start_gdb_session`, `gdb_console`, `gdb_session_status`, and `close_gdb_session` manage a persistent GDB/MI session in MCP. The one-shot CLI equivalent is `rea debug-with-gdb 'file ./program'`. MCP starts GDB with `--nx --quiet --interpreter=mi3`, retries initialization with MI2 if MI3 initialization returns an error and cleanup succeeds, waits for its prompt, and disables auto-loading. The console remains unrestricted and can run shell commands, change target state, access files, and use network in the REA process user's security context. Raw MI records and console/target/log streams are returned with Evidence; command output is retained up to 16 MiB and explicitly marked when truncated. Persistent GDB debugger sessions are unavailable on Windows because REA's owned Job Object cleanup cannot safely distinguish the debugger from its inferior processes.

Before a normal close, REA checks for live GDB thread groups. If any remain, select and apply a disposition to each inferior through `gdb_console` (for example, detach or kill as appropriate), then retry close. REA never infers target ownership from a PID or path. When the MCP server shuts down, REA terminates only its directly owned GDB process and reports target state as unknown.

```text
start_gdb_session {}
gdb_console {"session_id":"…","command":"file ./program"}
gdb_console {"session_id":"…","command":"info files"}
gdb_session_status {"session_id":"…"}
close_gdb_session {"session_id":"…"}
```

## Rizin

`execute_rizin_command` and `rea execute-rizin-command` run one selected command against a local artifact. The one-shot profile uses `-N -q -c`, suppressing user settings and scripts while leaving plugins available. Commands and plugins run with the REA process user's security context and may access files or the network or perform other actions. REA preserves raw output and does not claim that command-specific JSON has one universal schema.

`start_rizin_debug_session`, `rizin_debug_command`, `rizin_debug_session_status`, and `close_rizin_debug_session` provide persistent debug sessions through the MCP server. Rizin starts with `-N -0 -d`; an optional `backend` selects an IO debugger plugin and is retained in each command's Evidence. The [Rizin Handbook](https://book.rizin.re/src/first_steps/commandline_options.html) documents that `-0` emits a NUL after initialization and every command. Each NUL frame and each command's aggregate output are bounded to 16 MiB; queued output has both a 4 MiB charge limit and a 4096-frame limit that charges at least 64 bytes for every frame, including empty frames. Each command appends a unique completion marker, includes output interleaved before that marker as `command_and_interleaved_session_output`, and stops the owned debugger if the marker times out or unsolicited frames make correlation ambiguous. When output/frame capture overflows, REA returns the retained partial output with `output_truncated: true` and `completion_status: unknown`, then stops the debugger because command completion is uncertain. Session status keeps bounded recent output and reports when its history was truncated. Persistent Rizin debugger sessions are unavailable on Windows because REA's owned Job Object cleanup cannot safely distinguish the debugger from its inferior processes. Availability and target behavior depend on the installed Rizin build and backend. Closing stops only the directly owned debugger process and reports target state as unknown.

```sh
rea execute-rizin-command ./program iI
rea debug-with-rizin ./program dr
```

Static Rizin command stdout and stderr are each limited to 16 MiB (32 MiB combined); `output_truncated` marks output beyond either stream limit. Persistent debug commands use Rizin's documented `-0` framing and the manager resolves relative artifact paths to absolute paths before launch.

## Cutter

Cutter integration uses the REA-owned Python plugin in [`bridge/cutter/rea_bridge.py`](../bridge/cutter/rea_bridge.py). Use Cutter's plugin manager or the [official plugin guide](https://cutter.re/docs/contributing/plugins/getting-started.html) to locate the user Python-plugin directory for that exact build, copy `rea_bridge.py` there, then restart Cutter. The Cutter build must include Python plugin support and expose the `cutter` Python module with PySide2 or PySide6; upstream Cutter builds without the Python plugin build options cannot load this adapter. The official guide documents plugin discovery and the build options required for Python plugins. Cutter does not define the REA IPC protocol; the plugin opens a loopback-only TCP endpoint and publishes an authenticated descriptor in a per-user directory.

`list_cutter_sessions` discovers live instances, reports whether the bridge directory was verified as private, and returns Cutter's version string when the installed Python binding exposes it. POSIX checks the current user's owner and mode. Windows checks a protected DACL limited to the current user and SYSTEM; REA's native addon verifies the directory and opens descriptor files relative to that verified directory handle, rejecting reparse points and oversized files. The plugin publishes descriptors atomically. `cutter_command` takes the selected `session_id` and `expected_generation`; it rejects a generation when a different active-file path is observed at the command boundary. This generation is an observed path-change counter, not stable identity for tabs, unsaved documents, same-path reloads, or a path switch that occurs and reverses between observations.

Commands are unrestricted Rizin commands executed in the GUI thread with Cutter's user authority. They can change analysis, edit or save binary/project data, write files, use the network, or change the UI, depending on the command and loaded plugins. REA does not save or close automatically. The command itself can save when requested, for example `Ps /path/to/project.rzdb`, and load a saved project with `Po /path/to/project.rzdb`; these project commands are documented by [the Rizin Handbook](https://book.rizin.re/src/debugger/migration.html). Use a caller-selected destination and account for the command's effects. Each command returns raw provider output up to the 16 MiB bridge frame limit. If the response exceeds that limit, the bridge can omit the output; REA reports `execution_state: unknown` and `output_truncated: true`. If cancellation arrives before the command is sent, REA returns cancellation. After dispatch, the result is uncertain because Cutter's UI thread may still execute the command; REA closes the transport and reports `execution_state: unknown`, so do not retry automatically. If a UI-thread request times out, its result may still arrive later: REA reports the execution state as unknown and the plugin rejects later requests until Cutter restarts. A transport failure after REA sends a command also records execution as unknown and advises against automatic retry. Cutter/Rizin exceptions are conservatively marked unknown because an unrestricted command may have produced partial effects before raising.

```sh
rea list-cutter-sessions --format json
# Copy session_id and document_generation from a live entry in the result.
rea cutter-command '<session_id>' <document_generation> iI
```

For the automated smoke against an already-running upstream Cutter session, build REA, install the plugin, open a disposable local binary, and run `npm run verify:cutter`. This verifier checks discovery, records the version returned by Cutter's `getVersionInformation()` API, executes `ij` through CLI and MCP and compares their Evidence, adds a unique analysis comment at `entry0`, saves a temporary Rizin project with `Ps`, removes the in-memory comment, reopens the project with `Po`, verifies that the comment was restored, checks that the binary digest did not change, and removes the temporary project. It does not test document switching, stale-generation rejection, or Cutter shutdown; perform those as separate manual acceptance checks by opening a different artifact and checking that the old generation is rejected, then closing Cutter and confirming that listing reports no live session. Run the same real smoke on Linux, macOS, and Windows against upstream Cutter builds. A third-party device may host Cutter; its exact OS, Cutter release/build, plugin load result, and smoke output are required evidence for that platform claim. Cutter documents that Python plugins require `CUTTER_ENABLE_PYTHON` and `CUTTER_ENABLE_PYTHON_BINDINGS` at build time in the [official plugin guide](https://cutter.re/docs/contributing/plugins/getting-started.html). Cutter's version-specific Python bindings and GUI thread dispatch cannot be established by simulated bridge tests.

Set `REA_CUTTER_BRIDGE_DIR` to the same absolute directory in Cutter and REA when their user environments differ. On POSIX, the plugin opens the configured directory without following a final symlink, requires the current user to own it, and sets its mode to 0700 during startup, including when the directory already existed. It publishes descriptor files atomically with mode 0600. On Windows, bridge storage must be on a local NTFS fixed drive supported by REA's native file boundary; the plugin creates a protected current-user/SYSTEM DACL, and REA refuses to consume descriptors if the native ACL check is unavailable or fails. Descriptor files are limited to 64 KiB, read without following links, and checked for private ownership/access. The descriptor contains a per-process authentication token; tool results and logs do not expose it. The bridge remains experimental until its Python bindings, UI-thread dispatch, persistence, and document-change behavior have passed a real upstream lane for each claimed host/build. Upstream Cutter release builds document Python plugin support as build-option dependent; source-built and third-party builds can differ, and plugin loading must be observed in the exact release. The [`real-cutter.yml`](../.github/workflows/real-cutter.yml) workflow runs only when manually dispatched or sent the `real-cutter-upstream` repository event; it requires dedicated Linux/macOS/Windows self-hosted runners labelled `cutter-upstream`, with upstream Cutter and the REA plugin loaded and a disposable binary already open. Each runner must expose the same bridge directory to its Cutter and REA processes; configure `REA_CUTTER_EXPECTED_VERSION` in the runner environment when the lane should pin a specific build. The workflow's presence does not establish support: no platform is verified until that runner completes the real smoke successfully and publishes its `cutter-smoke.json` artifact. A third-party device can host these runners or run `npm run verify:cutter` manually; record the Cutter version and platform output. Local `cutter-re` package names or missing local Python bindings do not establish whether a different upstream Cutter build can load the plugin.

## Configuration and coverage

The optional `REA_OBJDUMP_COMMAND`, `REA_GDB_COMMAND`, and `REA_RIZIN_COMMAND` values select executable names or paths; otherwise REA searches `PATH`. Values are passed directly to process spawning, not expanded as shell command lines. Cutter uses `REA_CUTTER_BRIDGE_DIR` or a per-user default. Version and capability values are not inferred from documentation: they remain unknown until observed from the installed tool and verified in the corresponding real-provider lane.

Provider capture limits are separate from the MCP response budget. A result that fits an objdump/Rizin/GDB/Cutter provider limit may still exceed the default 10 MiB MCP response budget and return a transport `resource_constraint`. Configure `REA_MCP_MAX_RESPONSE_BYTES` to match a larger client receive buffer when that client supports one; otherwise use retained Evidence/export or complete CLI JSON output. See [MCP response limits](./mcp-contracts.md#tool-results). GDB and Rizin persistent sessions currently use REA's owned-process pipe launcher. That launcher does not support protocol stdin on Windows, so these session tools report unavailable there. Static objdump/Rizin command tools do not use that pipe launcher. The Cutter workflow verifies Cutter only; it does not establish objdump, GDB, or Rizin coverage. Those providers need separate host-native checks, and no platform/provider claim should be made without matching real verification evidence. Mock transport and package startup checks do not establish upstream Cutter or debugger support.
